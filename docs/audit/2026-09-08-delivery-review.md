# PsyTest: ревью и передача разработки, 08.09.2026

Пакет 07.18; исходный commit `d9999af`, ветка `codex/07-cabinets-audit`.
Это выборочное ревью кода и процесса, не клиническая валидация всех методик и не проверка рабочего сервера.

## Вывод

Рабочее ядро стоит сохранить: PHP/Twig, модульный контракт, отдельные calculators,
проверка типа токена и slug, lifecycle, общий renderer HTML/PDF и адаптер ИИ уже дают основу.
Переписывание на фреймворк, объединение всех сервисов и массовая чистка CSS сейчас не приближают
первый полезный сценарий. Главный разрыв — между реализованными техническими компонентами
и законченным действием специалиста: назначить тест, увидеть прохождение, открыть ответы и результат.

Владелец подтвердил 08.09: **СМИЛ и кабинеты параллельно**, свободные аналоги тоже остаются целью.
СМИЛ не заменяется IPIP. Оплата отложена. Новые агенты начинают с пакетов ниже, а не с повторного
общего аудита и чтения всего архива.

## Что готово и чего нет

| Направление | Факт | Остаток |
|---|---|---|
| Бесплатное прохождение | Пять модулей, результат, PDF, парный Лазарус | Сквозное назначение психологом |
| Кабинет специалиста | Вход, ручной поиск по result token, назначение therapist_case, удаление | Клиенты/список назначений, приглашения, просмотр ответов, редактор и одобрение отчёта |

| СМИЛ | Проверенное ядро; существующие дополнительные шкалы | Полный перечень источника, сверка 23 шкал, проверенные следующие пакеты |
| Открытые методики | Обзор и выбор IPIP в документах | Конкретная форма и русская версия, evidence, реализация |

Подробный инвентарь кабинетов: [отдельное ревью](2026-09-08-cabinets-review.md).

## Подтверждённые замечания

**R1 / P1 — клиентский режим не ограничивает выдачу ИИ.**
`controllers/ResultController.php:201–267`: заказ и polling проверяют result token/slug,
но не `therapist_case`, approval или consent; готовый текст отдаётся по статусу `ready`.
`core/Ai/AiReportGenerator.php:38–53` вызывает провайдера. Назначение therapist_case уже существует,
поэтому до подключения приглашений нужна единая политика заказа/просмотра для HTML и JSON.
Наличие опубликованного промпта не означает согласия конкретного клиента на передачу данных.
Это статически подтверждённый разрыв с PRODUCT_RULES §4/§11, а не свидетельство фактической утечки.
Проверить отрицательными HTTP-тестами без внешнего провайдера; нормативные тексты согласия
и объём контекста приносить владельцу, не сочинять разрешение в коде.

**R2 / P2 — версия задания не фиксирует реально использованный вход.**
`core/Ai/AiReportRepository.php:69–78` сохраняет prompt_version, но
`core/Ai/AiReportGenerator.php:38–42,72–105` снова берёт текущий published-промпт и живые результаты.
Если между постановкой и обработкой опубликована другая версия, сохранённый номер не описывает запрос.
Нужен неизменяемый разрешённый snapshot при постановке и тест «поставили v1 → опубликовали v2 →
обработали v1». Не отправлять сохранённый клинический контекст повторно без предусмотренного согласия.

**R3 / P2 — зависшее задание может стать вечным pending.**
`core/Ai/AiReportRepository.php:112–113,164–185`: releaseStuck возвращает задание в pending
независимо от attempts, а claimNext берёт только attempts < 3. После третьего обрыва такое
задание больше не выбирается. Нужен terminal failed при исчерпании попыток; проверки границы 2/3.
При доработке добавить условный переход статуса/lease, чтобы поздний worker не перезаписывал новый результат.

**R4 / P2 — CI не распознаёт новое хранилище ИИ как слой БД.**
`bin/classify-ci-scope.php` использует ручной список файлов. Изменение `core/Ai/AiReportRepository.php`
могло не включить DB matrix PR. В этом пакете добавляется regression case и консервативная
классификация AI-слоя; результат узкой проверки записан в WORKLOG.

**R5 / P2 — панели содержат взаимоисключающие текущие утверждения.**
STATUS одновременно называл этап 03 незакрытым и закрытым, prompt draft и published,
нагрузку СМИЛ отсутствующей и готовой. ARCHITECTURE называл новый AI и Module API v2 будущими,
хотя маршруты и код уже существуют. Последние commits 27.08 не попали наверх WORKLOG.
Исправляются актуальные сводки; исторические свидетельства остаются помеченной историей.
Серверный релиз указывается только как последний записанный `2e276b3` из BEGET_STAGING,
без утверждения о свежей проверке сервера.

**R6 / P2 — сборка читает рабочее дерево.**
`bin/build-release.sh:18–64`: clean git status не исключает ignored-файлы; rsync копирует всё,
что не попало в denylist. Возможность попадания локального ignored-артефакта следует из алгоритма,
новый артефакт в этом аудите не собирался. Отдельный build-пакет: git archive/allowlist,
fixture с ignored-файлом вне артефакта, сохранность всех tracked public assets.

**R7 / P1 — публичное удаление оставляет клинический AI-артефакт.**
`core/SessionManager.php:223–247` очищает test_sessions, но не ai_reports. Каскад БД
срабатывает только при физическом DELETE. Нужна транзакционная очистка content/owner_context
и защита от запоздавшего worker; regression case с готовым и выполняющимся отчётом.

**R8 / P2 — завершённый результат можно пересчитать повторным submit.**
`controllers/TestController.php:153–218` проверяет ID/slug, но не состояние partial
перед сохранением новых ответов. Повторный POST меняет основу уже заказанного отчёта.
В пакете целостности зафиксировать повторный submit/ответы завершённой сессии и snapshot;
проверить весь credential flow отдельными отрицательными тестами, не объявлять сам UUID
доказательством доступа постороннего пользователя.

## Чистота и простота

- Сначала устранять дублирование правил доступа и жизненного цикла. Общий policy/service для
  отчётов полезнее универсального контроллера для всех страниц.
- Не создавать отдельные calculators, копии PDF-рендеринга или параллельный SessionManager для кабинетов.
  Приглашение — отдельная сущность; `partner_token` пары не является приглашением психолога.
- В СМИЛ есть два набора дополнительных шкал (`additional-scales*.json`) и пути их загрузки
  (`SmilModule.php:294,353`). Это предмет карты происхождения/использования S1, а не повод удалить
  один файл или объединить ключи без доказательства. Корректность норм в этом ревью не пересчитывалась.
- Legacy services заморожены D-033. Их существование само по себе не дефект активного потока.
  Удалять только отдельным пакетом с проверкой всех usages, а не ради уменьшения числа строк.
- Контрактные тесты исходного текста полезны для документации, но не доказывают auth/ownership.
  `OwnerDashboardContractTest` и `SessionTestIntegrityTest` нужно дополнять сценарными тестами
  при изменении соответствующего поведения, без массового переписывания тестового набора.
- Cap PHPStan 147 — защита от роста, не доказательство чистоты. Снижать долг рядом с изменяемым кодом;
  самостоятельный большой cleanup не блокирует продуктовую работу.

worktrees; канонические панели объединяет один ведущий после результатов. Два DB-пакета
одновременно не меняют миграции. Модели: Terra/Claude для реализации, Luna для механического
инвентаря и запуска проверок; дорогой reviewer только на спорной границе доступа/клинического смысла.

**Начало следующей сессии:** S1 + K0 параллельно; K1 — сразу после K0.
O1 можно поручить свободному агенту отдельно, не вытесняя S1/K1. O2 следует за первыми
результатами двух основных линий. Ориентир полноты СМИЛ «около 110» из старого плана не является
обещанием точного числа: его устанавливает полный source inventory, а не произвольный лимит партии.

### Нерешённые вопросы — спрашивать в нужном пакете

K1: срок жизни приглашения; для пары — кому принадлежат приглашение/ответы каждого участника
и какое информирование требуется до привязки к психологу. Первый срез — индивидуальный Лазарус.
K3: почтовый провайдер, восстановление и retention после привязки/удаления аккаунта.
S1/S3: издание, расхождения и профессиональная приёмка. O1: конкретный опросник IPIP/перевод.
Реальные письма, внешний ИИ с данными клиентов и production не входят в поручение этого аудита.

## Как не повторить методологическую проблему

Для каждого пакета писать один видимый сценарий, 3–7 критериев приёмки и короткий evidence.
Зелёный gate не равен готовому кабинету. Перед передачей проверить сценарий от начала до конца,
ошибки доступа и пустые состояния. Новые общие элементы берутся из UI_KIT, а не получают
свои почти одинаковые классы. Один исполнитель меняет общий слой; остальные работают в своих модулях.
Не пересказывать накопленный WORKLOG в STATUS: текущая сводка сверху, история в журнале.
