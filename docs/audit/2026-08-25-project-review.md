## 2. Код: оценка и находки избыточности

### 2.1. Общая оценка — хорошая

Распределение: `core/` — 18 классов мелкими финальными классами с честными контрактами;
модули методик изолированы за `TestModuleInterface`; контроллеры тонкие; scoring СМИЛ
вынесен в `modules/smil/Scoring/` с golden-фикстурами. Ни одного класса-бога, ни одного
случая копипасты уровня логики между модулями. Трогать структуру не нужно.

### 2.2. Мёртвый PHP-код legacy-контура — ~930 строк

Замер по ссылкам из маршрутов и живых вызовов:

* **`controllers/ApiController.php`**: из 206 строк жив только `health()` (маршрут
  `/api/health`). `yoomoneyWebhook()`, `processInterpretation()`, `sendInterpretationEmail()`,
  `getResultUrl()` (~170 строк) **не маршрутизируются** — `/webhook/yoomoney` ведёт на
  `RetiredPaymentController`. При этом конструктор ApiController инстанцирует
  `PaymentService` и `AIInterpretationService`, то есть даже health-check тянет legacy-
  сервисы оплаты и ИИ. `LegacyPaidFlowContainmentTest` запрещает вернуть webhook на этот
  код — но сам код продолжает жить и проверяться PHPStan.
* **`controllers/ResultController.php:286–315`**: метод `interpretation()` недостижим
  (маршрут `/interpretation/{token}` ведёт на `RetiredPaymentController`) и ссылается на
  шаблон `interpretation-page`, **которого не существует** — при вызове упал бы. Это уже
  не «задел», а гарантированно сломанный тупик.
* **`services/AIInterpretationService.php` (272), `PaymentService.php` (256),
  `EmailService.php` (200)** — суммарно ~728 строк, вызываются **только** из мёртвого пути
  ApiController. Живых потребителей нет.

Итого ~930 строк кода, который существует, анализируется и поддерживается, но не может
быть исполнен легальным путём. Containment как *маршрутное* решение работает правильно;
containment как *сохранение тел методов* — дороже удаления.

Рекомендация (требует решения владельца, D-032-образного): сузить `ApiController` до
`health()` без тяжёлых зависимостей конструктора; удалить `ResultController::interpretation()`;
решить судьбу трёх сервисов — удалить или явно заморозить до этапа 06/07 с пометкой в
`ARCHITECTURE.md`. Маршруты уже закрыты, поэтому риск нулевой; обновить
`LegacyPaidFlowContainmentTest` соответственно.

### 2.3. Мёртвый фронтенд-контур графика — измеримо, на каждом просмотре пары

Замер: `templates/result-page.twig:87–90` (это живой шаблон страницы парного результата
`/pair/{id}`) загружает:

1. **Chart.js 4.4.0 с внешнего CDN** (~200 КБ);
2. `js/smil-profile.js` (184 строки) — рисует в `#smilProfileChart`;
3. `js/smil-scale-indicator.js` — активируется только если существует `#smilProfileChart`;
4. `js/smil-profile-classic.js` — рисует в `#smilClassicProfile`.

При этом **ни один шаблон и ни один PHP-класс не рендерит ни `#smilProfileChart`, ни
`#smilClassicProfile` на этом пути**: канонический график СМИЛ рендерится через
`blocks/profile-chart.twig` только на одиночной странице результата (`result-layout`),
которая сама Chart.js не грузит и грузит лишь classic-скрипт. Inline-блок scale-indicator
в `result-page.twig:91–111` зависит от несуществующего canvas и никогда не выполняется.
`results.js::initProfileChart` ищет тот же несуществующий `#smilProfileChart`.

Следствия: лишний внешний запрос к jsdelivr на каждом просмотре пары (для клинической
платформы это ещё и утечка IP посетителей третьей стороне без пользы), плюс ~10 КБ
локальных скриптов, которые физически не могут ничего нарисовать. PDF-генерация это не
затрагивает — она идёт через HTML/CSS `renderProfileChartHtml()`.

Рекомендация: убрать из `result-page.twig` Chart.js CDN, `smil-profile.js`,
`smil-scale-indicator.js` и мёртвый inline-блок (оставив classic-скрипт только там, где
есть блок графика). Обязательна браузерная проверка одиночного результата СМИЛ и парной
страницы после снятия — по правилам UI-пакетов этапа 04.

* Единственный web root `public/`, вход через front controller; CSRF на всех POST;

* Зависимости: 6 runtime, все оправданы (twig, dompdf, uuid, monolog, phinx).

### 3.2. Замечания (зафиксировать, не спешить)

1. **Шум в migration chain**: `20260816020000_add_crisis_resource_registry` и
   `20260822010000_add_ai_processing_consents` создают таблицы, которые следующая

   Сейчас — приемлемый trade-off за сохранение истории.

   решению; нужен явный пункт очистки в этапе 02/08, иначе доживут до продакшена.
3. **Module API v2 (этап 03)** — правильный ответ на накопленные специальные случаи

### 4.6. Нужен ли CI — ответ на вопрос владельца

**Да, нужен; убирать нельзя. Он уже стоит дёшево, и его дорогая часть давно условная.**

Замер по последним запускам (`gh run list`):

| Событие | Что гоняется | Длительность по факту |
|---|---|---|
| pull_request | быстрый gate (тесты без MySQL, PHPStan, lint, архитектура, baseline, audit) | **< 1 мин** |
| push в `main` | полный gate + матрица MySQL 5.7 и 8.0 + миграции | **1–6 мин** |
| PR слоя данных | + условная DB-матрица по классификатору `bin/classify-ci-scope.php` | ~2 мин |

Аргументы против удаления — из истории именно этого репозитория:

1. CI поймал дефекты, невидимые локально: дубль колонки `retention_class` в чистой цепочке
   миграций (02.1A), несовместимый implicit TIMESTAMP default MySQL 5.7 (08.1C),
   регистрозависимость autoload Linux (L-009). Локальная машина разработчика эти классы
   дефектов не воспроизводит в принципе.
2. Деплой на staging завязан на зелёный full-gate `main`; вместе с CI уходит и
   deployment-gate, и смысл rollback-точек.
3. Ваши же правила ставят цену ошибки расчёта выше скорости разработки; для клинической
   платформы автоматическая матрица БД — это не роскошь, а минимальная страховка.

Если цель — сэкономить ещё пару минут: единственная осмысленная опция — вывести MySQL 8.0
из каждого push в `main` (staging работает на 5.7) в ночной schedule. Я **не
рекомендую**: экономия ~2–3 минуты, а риск молча вернуть дефект класса 08.1C остаётся.
Текущая конфигурация — уже разумный баланс после 00K.

Где время теряется на самом деле: не в CI, а в (а) чтении документов на старте сессии —
уже сокращено 00F, (б) ручном gate-ритуале — локальные тесты идут ~2 секунды, полный gate
— минуты, и он окупается на первом же пойманном дефекте.
