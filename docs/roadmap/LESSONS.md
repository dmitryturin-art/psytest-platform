# Уроки и профилактика повторных ошибок

Назначение: не искать виноватого, а превращать каждую ошибку или ложное предположение в проверяемое правило процесса.

## Формат

Каждая запись содержит: наблюдение → риск → новое правило → автоматическая/ручная защита → статус.

## L-001 — Документация не доказывает фактическое поведение

- Наблюдение: README/ARCHITECTURE обещают CSRF, шифрование, 152-ФЗ, готовую оплату и другое число тестов, чем фактический код.
- Риск: ложное чувство готовности и неверные публичные обещания.
- Правило: current-state claims подтверждаются кодом/тестом; желаемое состояние находится только в roadmap.
- Защита: documentation truthfulness checklist в каждом work package; DOC-01 в traceability.
- Статус: действует.

## L-002 — Зелёный инструмент может скрывать долг

- Наблюдение: PHPStan сообщает `No errors`, но baseline подавляет 149 сообщений; architecture check падает из-за неверного root.
- Риск: метрика выглядит лучше фактического качества.
- Правило: фиксировать конфигурацию, baseline и реальный вывод, а не только зелёный статус.
- Защита: baseline metrics в `STATUS.md`, запрет увеличивать baseline, отдельное постепенное уменьшение.
- Статус: действует.

## L-003 — Нельзя доверять количеству дополнительных шкал и self-generated fixtures

- Наблюдение: metadata говорит о 200 шкалах, JSON содержит 23; у R/Es/Do нормы математически не согласуются с записанными ключами.
- Риск: профессионально выглядящий, но методически неверный результат.
- Правило: базовые 13 заморожены; дополнительные шкалы идут через traceable registry и независимый reference case.
- Защита: invariants, source/page, validation status, batches 10–20 и owner approval.
- Статус: действует; подтверждено agentmemory lesson с confidence 0.95.

## L-004 — UI-редизайн не даёт права менять профессиональный график SMIL

- Наблюдение: предыдущие нейросети неоднократно убирали разрыв и заменяли канонический профиль неуместными схемами.
- Риск: потеря профессионального смысла и доверия владельца.
- Правило: график — protected component; UI-этап меняет только polish вокруг него.
- Защита: golden chart data, desktop/mobile/print visual snapshots и отдельное owner approval для геометрии.
- Статус: действует.

## L-005 — Legacy payment нельзя «допочинить» без смены модели данных

- Наблюдение: текущий код смешивает YooMoney, YooKassa, заказ, платёж и готовый AI content; часть маршрутов/шаблонов отсутствует.
- Риск: двойные платежи, неверная выдача и неподтверждённые чеки.
- Правило: сначала отключить broken CTA, затем построить order/payment/job/report state machines заново.
- Защита: этапы 01, 06 и 07 разделены; webhook не запускает LLM синхронно.
- Статус: действует.

## L-006 — IP не является достоверной географией кризисной помощи

- Наблюдение: аудитория русскоязычная, но находится в разных странах; VPN/мобильные сети и поездки искажают IP.
- Риск: показать человеку неверный экстренный контакт.
- Правило: ручной выбор важнее IP; всегда есть unknown-country fallback.
- Защита: CountryResolver precedence, verified resource dates и browser tests.
- Статус: действует.

## L-007 — Большой набор планов без единой трассировки теряет решения

- Наблюдение: в проекте накопились активные на вид планы разных нейросетей и сред, включая устаревшие Superpowers-файлы.
- Риск: агент выполняет старый план или забывает finding аудита.
- Правило: один канонический roadmap, один active status, finding-to-phase matrix.
- Защита: source hierarchy в `ROADMAP.md`/`AGENTS.md`; архивные документы не имеют нормативной силы.
- Статус: внедряется этапом 00.

## L-008 — `.gitignore` не удаляет уже отслеживаемые чувствительные артефакты

- Наблюдение: два PDF с индивидуальными психодиагностическими результатами и старые browser/debug snapshots оставались tracked после добавления ignore rules.
- Риск: чувствительный или мусорный файл продолжает публиковаться и сохраняется в истории, хотя `git status` его больше не показывает.
- Правило: перед GitHub/release проверять `git ls-files`, а не только untracked status; generated result artifacts никогда не являются fixtures.
- Защита: pre-publication tracked-file scan; вывод из индекса с сохранением локальной копии; при реальных данных отдельно оценивать history purge и credential/link revocation.
- Статус: действует; текущие tracked artifacts выведены из индекса. Владелец признал два старых PDF обезличенными и отдельно решил не переписывать историю.

## L-009 — Проверять Composer autoload на Linux, не доверять macOS case-insensitivity

- Наблюдение: модуль Лазаруса загружался на macOS, но реальный Linux CI сообщил `Class ... LazarusModule not found` из-за lowercase-каталога и отсутствующей явной PSR-4 mapping.
- Риск: локально зелёные тесты и падение production/CI на Linux.
- Правило: после нового или перемещённого модуля явно проверить его PSR-4 mapping или привести путь к PSR-4; выполнить `composer dump-autoload --optimize` и иметь regression-test `class_exists`.
- Защита: Linux CI и `tests/LazarusAutoloadTest.php`.
- Статус: действует.

Дополнение процесса: незакоммиченные изменения нельзя оставлять на `main`; если это произошло, сразу создать отдельную `codex/...`-ветку до staging/commit.

## L-010 — Нельзя добавлять один schema-index и в bootstrap, и в инкрементальную миграцию

- Наблюдение: `uq_partner_token` оказался одновременно в `InitSchema` и в `AddPairInviteUniqueness`; чистый GitHub MySQL поднял bootstrap, а затем получил ошибку 1061 на повторном `ADD UNIQUE KEY`.
- Риск: локальная логика и unit-тесты могут быть зелёными, но новый production/staging database невозможно развернуть.
- Правило: каждое schema-изменение должно иметь один явный путь в migration chain; изменение bootstrap допускается только вместе с проверкой, что последующие миграции не повторяют DDL.
- Защита: перед публикацией schema package запускать чистые migrations и иметь regression, который проходит весь chain; GitHub migration step остаётся release gate.
- Статус: действует; исправление и regression запланированы как 01.5C.

## L-011 — Web root требует allowlist, а не надежды на «служебный» файл

- Наблюдение: `public/demo.php` раскрывал версию PHP и устаревшие claims, а `public/test-smil.php` создавал тестовые sessions без нормального production flow.
- Риск: диагностическая страница становится публичной surface и обходит бизнес-ограничения, даже если основной router безопасен.
- Правило: единственный PHP-entrypoint production web root — front controller; diagnostic harness не должен находиться в `public/`.
- Защита: `PublicWebRootTest`, HTTP/browser regression 404 и проверенный deployment document root.
- Статус: действует с `21c77c7`.

## L-012 — Regression должен проверять место security-guard, а не только его наличие

- Наблюдение: первая версия PAIR-02 test проверяла наличие вызова, но не его scope; guard оказался в обычном `submit` и был пойман до commit.
- Риск: «зелёный» source-level test подтверждает текст, но пропускает поломку соседнего flow.
- Правило: для route-specific security guard тест обязан ограничить ожидаемый метод/flow и явно исключить соседний.
- Защита: `SessionTestIntegrityTest` проверяет наличие binding в `pairSubmit` и отсутствие в normal `submit`; полный test gate перед публикацией.
- Статус: действует с `1cc772e`.

## Как добавлять урок

Добавить запись, если произошло хотя бы одно:

- неверное предположение привело к переделке;
- тест прошёл, но не проверял нужный риск;
- документация направила не в тот файл/flow;
- изменение повредило ранее утверждённое поведение;
- production/staging операция потребовала отката;
- ignore rule скрыл локальный файл, который уже оставался tracked;
- владелец повторно исправил одно и то же понимание продукта.

После записи обновить связанное правило/тест; один текст урока без профилактики не считается самообучением.
