# Production Runbook — выкладка PsyTest в продакшен

Статус: **черновик готов, go-live не начат**. Production-сервер и домен ещё не созданы;
этот документ фиксирует процедуру заранее, чтобы go-live был исполнением чек-листа,
а не импровизацией. Процедура основана на отработанной staging-последовательности
([BEGET_STAGING.md](BEGET_STAGING.md)) и репетиции восстановления от 25.08.2026 (L-015, 08.1G).

## 0. Предварительные условия (владелец, до первого деплоя)

- [ ] Production-хостинг/домен создан; PHP сайта выставлен в **8.3** (не ниже — требование `composer.json`).
- [ ] Отдельная production-БД; учётные данные передаются через локальный `.env` (не чат/не Git).
- [ ] DNS указывает на хостинг; TLS-сертификат выпущен; HTTPS-редирект подтверждён.
- [ ] `APP_ENV=production`, `APP_DEBUG=false`, payment/AI/owner-dashboard выключены до своих этапов.
- [ ] Cleanup-cron настроен по [CRON_CLEANUP.md](CRON_CLEANUP.md) (после первого релиза, когда появится `current`).
- [ ] Юридическая проверка privacy-текстов выполнена (см. DATA_MAP, открытые вопросы).

## 1. Сборка и выкладка релиза

Идентично staging (полная последовательность из 8 шагов — в
[BEGET_STAGING.md, «Сборка релиза»](BEGET_STAGING.md)):

1. `bin/build-release.sh` — артефакт + верификация полноты `public/` + sha256.
2. Загрузка, сверка checksum, распаковка в `releases/<sha>/`, копия `.env` (chmod 600).
3. **Pre-migration dump обязателен** → `backups/pre-deploy-<sha>.sql.gz`.
4. `php8.3 vendor/bin/phinx migrate` — только после дампа.
5. Атомарное переключение `public_html` + обновление симлинка `current`.
6. Smoke: `/api/health`, главная, одна живая страница результата, пустые error-логи.

## 2. Откат

- Откат кода: `public_html` → `releases/<предыдущий>/public` (секунды, без даунтайма сверх переключения).
- Откат данных: восстановление pre-deploy дампа. Проверено drill-ом 25.08.2026:
  дамп импортируется целиком (8/8 таблиц, построчная сверка count совпала).
- Политика: откат кода предпочтителен; откат данных — только при повреждении данных,
  потому что уничтожает изменения, сделанные после дампа.

### Восстановление дампа (проверенная процедура)

- В **отдельную** базу (создаётся в панели): `zcat dump.sql.gz | mysql <новая_бд>`. Целевая
  процедура DR — именно эта.
- В **ту же** базу (репетиция/проверка): все имена таблиц и `CONSTRAINT` переименовываются
  префиксом `drill_` через sed (иначе конфликт имён FK-констрейнтов — InnoDB требует
  уникальности в пределах базы; поймано drill-ом 25.08). После проверки drill_-таблицы удаляются.

## 3. Известные границы (честно, до закрытия этапа 08)

- Мониторинг/алертинг ещё не настроены (health-endpoint есть, автоматических алертов нет).
- Backup-схема: ежедневные автоматические бэкапы Beget (база + файлы, восстановление через панель)
+ pre-deploy дампы на каждый релиз (точка отката миграций, проверены drill-ом 08.1G). Свой ночной
  дамп не требуется — решение владельца 25.08. На go-live drill: один раз восстановить из
  панельного бэкапа Beget, чтобы знать процедуру и срок хранения копий.
- Фискальные настройки YooKassa — этап 06, до него payment остаётся выключенным.
- Юридическая проверка privacy copy — перед публичным запуском.
