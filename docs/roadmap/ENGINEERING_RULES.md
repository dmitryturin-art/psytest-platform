# Инженерные правила PsyTest

## Карта чтения по типу пакета

| Тип пакета | Прочитать обязательно |
|---|---|
| Psychometrics / scoring / нормы | §6 |
| Security / данные / приватность | §9 |
| UI / шаблоны / CSS | §7 и первые три раздела [`UI_KIT.md`](../UI_KIT.md) |
| Архитектура / модули | §8 |
| Оплата / ИИ | §9–10 |
| Выкладка на staging | §9 «Выкладка на staging» |
| Работа через субагентов | §4C |

Общие правила веток, коммитов, проверки и отчёта применяются всегда; не читать остальные разделы «на всякий случай».

## 1. Единица работы

Каждое изменение оформляется как небольшой work package внутри одного roadmap-этапа.

Work package обязан иметь:

- короткую цель и audit/phase references;
- явно включённый и исключённый scope;
- риск: low/medium/high/clinical/financial/security;
- способ проверки до начала реализации;
- acceptance criteria;
- отдельную ветку и один или несколько небольших коммитов;
- обновление статуса и документации.

Нельзя объединять «заодно» payment rewrite, CSS cleanup, scoring changes и security hardening.

## 2. Ветки

Формат: `codex/<phase>-<short-slug>`.

Примеры:

```text
codex/01-disable-broken-paid-flow
codex/01-token-boundaries
codex/04-design-system-shell
codex/05-smil-additional-scales-batch-01
codex/06-yookassa-orders
```

Правила:

- `main` всегда остаётся точкой интеграции, прямые изменения запрещены;
- один work package — одна ветка; крупный этап состоит из нескольких веток;
- новая ветка создаётся от актуального принятого baseline;
- worktree используется при реальной параллельной работе, но не обязателен для последовательной;
- force-push, history rewrite и destructive reset без прямого разрешения запрещены;
- ветка не смешивается с чужими незавершёнными изменениями.

## 3. Коммиты

Формат: `type(scope): result`.

Допустимые type:

- `docs` — документация и решения;
- `test` — тесты/fixtures без product change;
- `fix` — исправление дефекта;
- `refactor` — изменение структуры без изменения поведения;
- `feat` — новая возможность;
- `chore` — housekeeping;
- `build` — зависимости/сборка;
- `ci` — проверки CI.

Требования:

- один intent на коммит;
- сообщение описывает результат, а не «changes»;
- generated/cache/log/debug artifacts не коммитятся;
- secrets и персональные данные не коммитятся даже временно;
- перед коммитом выполнить `git diff --check`, просмотреть staged diff и `git status --short`;
- не использовать `git add .` вслепую; добавлять точные файлы;
- если work package требует миграции и кода, коммиты могут быть разделены, но ветка должна оставаться проверяемой на каждой контрольной точке.

## 4. Порядок выполнения work package

1. Прочитать `STATUS.md`, active phase, product rules и audit references.
2. Для незнакомой подсистемы выполнить релевантную навигацию: Graphify только после проверки свежести; при stale — прямое чтение и документированный fallback. Memory recall нужен при связи с ранее решённой задачей, не автоматически.
3. Проверить текущие изменения и воспроизвести baseline.
4. Для дефекта — получить failing regression test или документированный воспроизводимый сценарий.
5. Реализовать минимальный связный change.
6. Запустить узкие проверки, затем подходящую часть полного gate.
7. Для UI — проверить browser flows и screenshots; для данных — migrations/rollback; для платежей — provider fixtures.
8. Просмотреть diff как reviewer: безопасность, регрессии, дубли, сложность, документация.
9. Добавить запись в `docs/roadmap/WORKLOG.md` в раздел текущей даты (наверх внутри даты): этап/ветка/commit, цель, сделано, evidence. Затем обновить work packages/exit criteria active phase, `STATUS.md`, `AUDIT_TRACEABILITY.md`, при закрытии этапа — таблицы статусов `ROADMAP.md` и `docs/roadmap/README.md`, и при необходимости `ARCHITECTURE.md`. Work package без записи в WORKLOG считается незавершённым.
10. Сделать точный коммит и передать владельцу результат/риски/следующий шаг по протоколу прозрачности.

## 4A. Протокол прозрачности работы

Владелец должен в любой момент понимать: идёт ли работа, что именно выполняется, почему она остановлена и что будет дальше.

### Когда сообщать

- В начале work package: назвать `этап → подэтап/work package → branch`, цель и ближайшую проверку.
- Не реже чем раз в 60 секунд во время долгой работы: коротко сообщать фактическое состояние, без обещаний «в фоне».
- После завершения каждого work package: сообщить, что сделано, commit, merge/push/CI status, известные ограничения и **точный следующий номерованный шаг**.
- О субагентах сообщать только по прямому вопросу владельца или если их состояние создаёт реальный блокер. Не создавать видимость параллельной работы, если агентов нет.
- При остановке: явно написать `Статус: остановлено` и причину — выбор владельца, внешний сервис, ошибка или технический блокер.

### Автономное продолжение

Фраза владельца «работай по плану», «продолжай» или равнозначная — это разрешение самостоятельно переходить к следующему безопасному work package и **не ждать подтверждения после каждого коммита**. Вопрос задаётся только по правилам «Когда нужен вопрос владельцу».

Контрольная точка — не остановка: после неё ведущий агент сообщает следующий шаг и продолжает, если нет блокера.

### Честное состояние

- `Работаю` означает, что агент сейчас выполняет команды или анализ в активном сообщении.
- После итогового ответа фоновая работа не продолжается сама по себе. Это нужно прямо назвать, а не создавать обратное впечатление.
- Если внешний CI/сервис выполняется, указывать его URL/run ID, последнее известное состояние и когда будет следующая проверка.
- Формат итогового статуса: `Готово` → `Проверки` → `Следующий шаг N` → `Статус: продолжаю / остановлено`. Сведения о субагентах добавляются только по прямому вопросу или при блокере.

## 4B. Исполнение после ревью

- Вход для команды «продолжай» — START_HERE.md. Ревью является evidence, не второй очередью задач.
- Findings переводятся в ограниченные пакеты с исходными файлами, failing-сценарием и критерием приёмки.
- Исполнитель берёт следующий незавершённый пакет, а не заказывает новый общий аудит.
- Клиентский сценарий считается готовым после сквозной проверки; наличие миграции/сервиса/зелёного lint недостаточно.
- Для доступа, удаления и очередей нужны поведенческие отрицательные тесты; текстовые assertions их не заменяют.
- Сбой Docker/DNS/socket сначала классифицируется как возможное ограничение среды; подтверждение причины и разрешённый повтор обязательны до объявления baseline сломанным.
- Долг чистоты исправляется рядом с затронутым правилом. Самостоятельное объединение работающих scoring/renderer слоёв ради числа строк не входит в продуктовый пакет.

## 4C. Субагенты-исполнители (правила с 06–08.10.2026)

Сверх §10 «Оркестрация субагентов». Применяется, когда ведущий поручает исполнителю пакет с записью в репозиторий.

- **Изолированный worktree от `origin/main`**, отдельная ветка `codex/<phase>-<slug>`; общий каталог проекта исполнитель не трогает.
- **Своя база данных** `psytest_wt_<пакет>`; чужие и основные базы не используются. Если исполнитель случайно применил миграцию к чужой базе, он сообщает об этом в отчёте.
- **Номера миграций Phinx назначает ведущий заранее**, у параллельных пакетов они различаются; исполнитель не выбирает версию сам.
- **Файл `.env` не читается ни частично, ни целиком**: никакого `cat`, `grep`, `head`, `cut`, `sed`, `tr` по нему и никакого вывода значений. Нужное значение проверяется командой, которая не печатает его (например, тестом «переменная задана»). Случай 08.10: `cut -c1-40` по `.env` напечатал часть пароля deploy-аккаунта — пароль пришлось менять.
- **Исполнитель не правит** `WORKLOG.md`, `STATUS.md`, `CHANGELOG.md`, phase-файлы, `ROADMAP.md`, `DECISIONS.md`: журнал и панели ведёт и объединяет ведущий. Исполнитель вместо этого отдаёт в отчёте «что записать»: цель, сделано, решения, проверки, риски. Документы по устройству кода (`ARCHITECTURE.md`, `DATA_MAP_CURRENT.md`, `UI_KIT.md`) правятся в пакете.
- **Коммиты** — в своей ветке исполнителя; слияние в `main`, push и выкладка остаются за ведущим (уточнение к §10: запрет «не коммитит» относится к общему каталогу, не к изолированному worktree).
- **Независимая рецензия безопасности и приватности** (отдельный агент, который не писал код) обязательна для пакета, затрагивающего ссылки и токены, передачу данных ИИ-провайдеру или удаление данных. Замечания HIGH и MEDIUM закрываются до слияния, LOW — закрываются или записываются в долг.
- **Дизайн-критика** обязательна для интерфейсного пакета: исполнитель использует навыки `frontend-design` и `design` (критика, дизайн-система, тексты), приводит снимки «было / стало» на 1440 и 375 и описывает исправленное по критике.
- Ведущий просматривает снимки открытых меню и диалогов, а не только закрытых экранов, и запускает `bin/local-gate.sh` на объединённой ветке.
- Если два пакета сливаются вместе, полный gate запускается на объединённом `main`: CI проверяет ветки по отдельности и не видит их взаимодействия (случай 08.B47: WP9b + D5).

## 5. Тестовая стратегия

### Общий gate

```bash
composer validate --strict --no-check-publish
composer audit
composer migrate
composer test
composer analyse
composer lint
php bin/check-architecture.php
composer baseline:check
```

Не все команды сейчас исправны; этап 00 фиксирует baseline, а этап 01 чинит gate. До этого каждый отчёт явно разделяет старые поломки и новые регрессии.

`bin/check-module.php --all` не является текущей командой: скрипта в репозитории нет. Его нужно создать только вместе с модульным контрактом в этапе 03, а до этого не выдавать такой gate за рабочий.

### По типу риска

- Psychometrics: unit + golden/reference fixture + provenance review.
- Security: отрицательные HTTP tests и boundary cases.
- Database: migration up/down, transaction, idempotency/concurrency.
- Payment: sandbox/provider fixtures; production network запрещён до gate этапа 06.
- AI: schema, grounding, missing data, timeout/retry, cross-report consistency, evaluation fixtures.
- UI: keyboard, mobile 390×844, desktop, empty/error/loading/success states.
- PDF/email: content snapshot, Unicode/fonts, page breaks, exact revision delivery.
- Deployment: smoke, health, backup/restore, rollback rehearsal.

Тест, который только повторяет текущую реализацию или использует self-generated expected values, не считается независимым доказательством корректности.

## 6. Psychometric change control

- Базовые 13 шкал SMIL и scoring Lazarus защищены golden tests.
- Изменение ключа, нормы, формулы или threshold — отдельный clinical-risk work package.
- Обязательны edition, source page, до/после profile и объяснение расхождения.
- OCR или копия с сайта являются входом для проверки, но не финальным подтверждением.
- Дополнительные шкалы SMIL добавляются пакетами 10–20 и имеют validation status.
- Нельзя менять expected fixture, чтобы «починить красный тест», не доказав новое ожидаемое значение.

## 7. UI change control

- До общей реализации создаются 2–3 прототипа ключевого пути: каталог → тест → бесплатный результат → выбор разбора.
- Владелец выбирает направление; только после этого строится design system.
- Канонический SMIL profile chart выделен в protected component с visual regression.
- Новый CSS не добавляется в бесконечный общий файл без решения о структуре слоя.
- Проверяются тексты, hierarchy, empty/error/loading, focus, touch, print/PDF.
- Временный красивый mock не считается готовым, пока он не использует реальные данные и состояния.

### Обязательный порядок интерфейсного пакета (с 08.10.2026)

1. Первым делом прочитать разделы [`UI_KIT.md`](../UI_KIT.md) «Принципы вёрстки», «Принципы удобства» и «Сетка и ритм страниц кабинета», затем раздел с нужным элементом.
2. Использовать готовые классы и токены. Свой класс заводится, только если нужного нет в описи, и тогда сразу вносится в `UI_KIT.md`. Цвета, отступы и размеры — только через токены.
3. Проверить результат в реальном браузере на **1440 и 375 px** до открытия PR — без исключений для мелких правок и замены слов (случай 08.10: правка формулировок без проверки дала «прилипшую» кнопку и «зависший» флажок).
4. Измерить ширину каждого блока колонки: все равны ширине колонки, кроме абзацев прозы; `scrollWidth` на 375 равен 375; смотреть открытые меню и диалоги, а не только закрытые экраны.
5. Проверить пустое, ошибочное и загружаемое состояния и работу без JS там, где она обещана.
6. Тексты для владельца пишутся без жаргона разработчика и без голых английских ключей («заводской текст», «тестовые данные» вместо `manifest`, `fixture`, «синтетический набор»). Технические названия остаются только в технической документации.
7. Страница результата СМИЛ и клиентская страница результата сохраняют прежнюю компоновку (D-061); допустимы точечные добавления.

## 8. Архитектура

- `ARCHITECTURE.md` — current-state document; будущие идеи находятся в roadmap.
- Общий код не ветвится по test slug, если поведение можно выразить capability/schema/renderer.
- Контроллеры координируют, domain/service объекты реализуют правила.
- Миграции — source of truth для БД; snapshot schema генерируется или синхронизируется осознанно.
- Интеграции скрыты за adapters; provider-specific payload не протекает в test handlers.
- Значительные зависимости добавляются только с объяснением ценности, maintenance/security cost и вариантом отказа.
- Big-bang rewrite требует отдельного ADR и доказательства критериев из аудита.

## 9. Безопасность и данные

- Доступ сначала проверяется read-only resolution по точному типу token; универсального OR lookup быть не должно.
- Все state-changing web routes защищены CSRF, кроме отдельно проверяемого provider webhook.
- Логи не содержат answers, report text, email, tokens, provider secrets или raw webhook payload.
- Production defaults fail closed.
- Test/dev БД отделены от production данных.
- Удаление/retention проверяются интеграционными тестами.
- Точный IP не хранится без отдельной доказанной цели.

### Выкладка на staging

Подробный рецепт и история — [`BEGET_STAGING.md`](BEGET_STAGING.md) (п. 42 и «Сборка релиза»), общий порядок — [`PRODUCTION_RUNBOOK.md`](PRODUCTION_RUNBOOK.md).

- **Одна выкладка — одно SSH-подключение** с `-o NumberOfPasswordPrompts=1`. Все шаги выполняются в одном сеансе, без ControlMaster и без разовых «проверочных» входов.
- Шаги сеанса по порядку: архив из `bin/build-release.sh` передаётся через stdin; сверка SHA-256 с локальной суммой; распаковка в `releases/<sha>/` с `--strip-components=1`; копия `.env` из предыдущего релиза (`chmod 600`); дамп БД `backups/pre-deploy-<sha>.sql.gz` с проверкой `gzip -t` **до** миграции; `phinx migrate`; атомарное переключение `public_html` и `current`; смоук по HTTP (`/`, `/api/health`, `/admin/login`, закрытая методика отвечает 404). Любой сбой до переключения оставляет прежний релиз.
- Логин и пароль берутся командой, которая не печатает значения; в командах не используются `tr`/`sed`-приёмы, ломающие символы на macOS (случай 06.10, WORKLOG 08.B37: `\x` в `tr` удалил буквы из логина), а CR в пароле из `.env` удаляется.
- **При «Permission denied» выкладка останавливается**: повторов, смены способа входа и поиска обходных путей нет; ведущий сообщает владельцу, что стенд отклонил вход, и ждёт его решения.
- Перед выкладкой пакетов, слитых вместе, `bin/local-gate.sh` проходит на объединённом `main`.
- В записи WORKLOG выкладки фиксируются: runtime-sha, SHA-256 архива, размер дампа, список миграций, результаты смоука и **точная команда отката** (прежние `public_html` и `current`, при миграции — `phinx rollback -t <версия>`).

## 10. Работа с ИИ и навыками

- Навык используется, когда он даёт конкретную пользу задаче; наличие навыка само по себе не является причиной.
- Superpowers не обязателен и не применяется автоматически.
- Graphify — навигация, а не доказательство: важные факты проверяются по коду/источнику.
- Graphify freshness — обязательная техническая дисциплина: в начале сессии и после work package, меняющего код, шаблоны, CSS или документацию, запускается `php bin/check-graphify-freshness.php`. Статус `STALE` требует инкрементного обновления до следующего архитектурного query; если это временно невозможно, stale-граф не используется как доказательство, а причина, fallback и дата повтора фиксируются в `WORKLOG.md`.
- Обновление графа не запускает внешнюю модель самовольно: смысловую extraction при необходимости выполняют доступные bounded agents либо проверенный провайдер. Автоматизировать можно проверку свежести, но не неконтролируемый расход внешних ключей/лимитов.
- Agentmemory хранит решения и уроки, но не заменяет Git и канонические документы.
- Вывод ИИ не принимается без тестов/источников там, где затронуты клинический смысл, деньги, безопасность или production.

### Вызовы модели (с 08.10.2026)

- **Реальный провайдер не вызывается ни из тестов, ни из QA, ни из проверок в браузере**: используется заглушка/фейковый транспорт либо `ai_enabled=0`. Единственное исключение — пробный разбор владельца в кабинете на синтетических данных (D-071).
- **Длинные вызовы модели никогда не выполняются внутри веб-запроса**: запрос ставит задание в очередь (`ai_reports`, `ai_trial_runs`), воркер обрабатывает его отдельно, страница опрашивает статус. Причина: прокси хостинга обрывает ответ дольше таймаута (504), а повторные нажатия дают повторные платные запросы.
- Внешней модели уходит только обезличенный структурированный контекст; ответы по пунктам — по явной галочке методики (кроме утверждённого разбора Лазаруса). Контекст без имени, email, заметки, идентификатора сессии и токена.

### Оркестрация субагентов

Перед каждым work package ведущий агент **обязан оценить делегирование**. Независимые read-only inventory/link/test-log/review проверки выполняются субагентами, если доступны свободные слоты; исключение — постановка и проверка объективно дороже самой задачи. Если есть две и более независимые bounded-задачи, их следует запускать параллельно, когда это сокращает время или расход дорогой модели без потери качества.

Предпочтительно делегировать быстрым/экономичным моделям:

- поиск файлов, usages, дублей и устаревших ссылок;
- сверку документации с уже определённым источником истины;
- запуск и классификацию независимых test/lint logs;
- browser/viewport smoke по готовому checklist;
- review небольшого diff по заранее заданным критериям;
- сбор инвентаря, матрицы или evidence без продуктового решения.

Ведущий агент оставляет за собой:

- декомпозицию, архитектурное решение и интеграцию результата;
- clinical/psychometric judgement и выбор источника нормы;
- security/payment/privacy threat decisions;
- финальное редактирование пересекающихся файлов, staged diff и публикацию;
- любые production или необратимые действия.

Выбирать самый дешёвый класс модели, достаточный для задачи: быстрый (`gpt-5.6-luna`) — механические проверки и инвентарь; сбалансированный (`gpt-5.6-terra`) — самостоятельный bounded code/review; ведущая модель — неоднозначная архитектура и high-risk интеграция. Это ролевые ориентиры: при изменении доступных моделей выбирается актуальный эквивалент, а не устаревшее торговое имя.

Правила совместной работы:

- субагент получает точный scope, ожидаемый формат и запрет на лишние действия;
- read-only анализ можно распараллеливать свободно; запись разрешается только в явно непересекающиеся файлы;
- два агента не редактируют один файл одновременно;
- субагент не коммитит, не мержит, не пушит и не работает с production без отдельного поручения;
- ведущий проверяет вывод по репозиторию, устраняет противоречия и запускает итоговый gate;
- не создавать субагента для задачи, которая короче постановки/проверки или требует постоянного общего контекста.

## 11. Документация

Перед началом work package перечислить файлы, которые будут прочитаны, и обосновать каждый сверх обязательных трёх. Прочитанное «на всякий случай» — такой же незаявленный расход, как незакоммиченный файл. В отчёте по пакету указывать фактически прочитанное.

В каждом work package проверить:

- `WORKLOG.md` — запись пакета добавлена в раздел текущей даты (наверх), evidence приложен;
- `STATUS.md` — что сейчас происходит; панель синхронизирована с фактом;
- active phase — checklist и evidence;
- при закрытии этапа — таблицы статусов `ROADMAP.md` и `docs/roadmap/README.md`;
- `AUDIT_TRACEABILITY.md` — покрытые findings;
- `DECISIONS.md` — новые продуктовые/архитектурные решения;
- `ARCHITECTURE.md` — изменилось ли фактическое устройство;
- `README.md`/`DEVELOPMENT.md` — изменился ли пользовательский или developer flow.

Нельзя оставлять ложные claims о CSRF, 152-ФЗ, шифровании, количестве тестов или готовности оплаты.

## 12. Review и передача владельцу

Финальное сообщение work package содержит:

- что изменено и для чего;
- какие файлы/flows затронуты;
- свежие проверки и их результат;
- что сознательно не сделано;
- риски/решения, требующие владельца;
- commit/branch и следующий безопасный шаг.

Вопрос владельцу задаётся до изменения scoring, клинического текста, публичного обещания, фискальной конфигурации, production или protected SMIL chart. Остальные обратимые решения принимаются инженером внутри утверждённого scope.
