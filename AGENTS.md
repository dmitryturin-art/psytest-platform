# AGENTS.md — PsyTest Platform

## Назначение

PsyTest — модульная PHP-платформа психологического тестирования для практики клинического психолога. Ошибка в расчёте, доступе к результату или клиническом сообщении важнее косметической скорости разработки.

## Обязательный старт сессии

**Всегда (четыре источника, ~20 КБ):**

1. Новейшие записи `docs/roadmap/WORKLOG.md` (верхняя дата) — фактическая хронология пакетов с evidence.
2. Phase-файл активного пакета — только его, не всех активных этапов.
3. `docs/roadmap/STATUS.md` и таблица этапов в `ROADMAP.md` — оперативные панели. Они могут отставать от факта: сверять с п.1 и phase-файлом; при расхождении верить WORKLOG/phase-файлам, а расхождение панелей фиксировать в отчёте пакета и исправлять в нём же.
4. `git status --short`, `git log --oneline -10` и `git diff` — не перезаписывать чужие изменения.

**По типу пакета (таблица разделов — в шапке каждого файла правил):**

- psychometrics / scoring / нормы → `PRODUCT_RULES.md` §8–9, `ENGINEERING_RULES.md` §6;
- security / данные / приватность → `PRODUCT_RULES.md` §10–11, `ENGINEERING_RULES.md` §9;
- UI / шаблоны / CSS → `PRODUCT_RULES.md` §12, `ENGINEERING_RULES.md` §7;
- архитектура / модули → `ARCHITECTURE.md`, `ENGINEERING_RULES.md` §8;
- оплата / ИИ → `PRODUCT_RULES.md` §3, §5–6.

**По необходимости, а не по умолчанию:**

- Graphify freshness + query — когда пакет трогает незнакомую подсистему, а не всегда.
- agentmemory / lesson recall — когда задача похожа на ранее решённую.
- `AUDIT_TRACEABILITY.md` — когда пакет закрывает пункт аудита.
Если файл не прочитан — это указывается в отчёте, а не компенсируется чтением «на всякий случай».

`docs/roadmap/AUDIT_TRACEABILITY.md` читается только при закрытии конкретного audit finding.

## Приоритет инструкций

1. Последнее прямое решение пользователя.
2. `PRODUCT_RULES.md` и `DECISIONS.md`.
3. Активный phase-файл.
4. Технический аудит.
5. `ARCHITECTURE.md` и фактический код.
6. Остальная документация.

`docs/archive/` и `docs/superpowers/` — исторические материалы. Superpowers не является обязательной методологией и не используется без прямой просьбы пользователя.

## Неподвижные ограничения

- Все тесты и базовые результаты бесплатны.
- Платен только необязательный расширенный разбор поддерживаемых сложных методик.
- Проверенное scoring core SMIL и Lazarus не меняется без воспроизводимого дефекта.
- Канонический SMIL-график сохраняет L/F/K, визуальный разрыв и 1–9/0; никаких radar/bar replacements.
- Внешний ИИ получает только явно разрешённый структурированный контекст.
- Клиент терапевта не получает неодобренный ИИ-черновик.
- Секреты не попадают в Git, логи, Markdown, screenshots или tool output.

## Работа по этапам

- Один work package — одна ветка `codex/<phase>-<short-slug>`.
- Не смешивать security, payment, psychometrics и массовый UI cleanup в одном diff.
- Начинать с baseline и failing/regression test, когда поведение меняется.
- Для psychometrics использовать golden/reference fixtures; изменения ожидаемых значений требуют источника, объяснения и одобрения владельца.
- Для bugfix сначала воспроизвести первопричину, затем сделать минимальное исправление.
- Для архитектурной миграции использовать adapter/strangler-переход, если big-bang rewrite отдельно не одобрен.
- После каждого work package добавлять запись в `docs/roadmap/WORKLOG.md` (этап/ветка/commit, цель, сделано, evidence) в раздел текущей даты наверх файла — до checkpoint или передачи владельцу. Пакет без записи в WORKLOG считается незавершённым; «записать потом» — нарушение журнала.
- После каждого work package обновлять `STATUS.md`, work packages/exit criteria активного этапа, traceability и архитектуру при необходимости; при закрытии этапа синхронизировать таблицы статусов в `ROADMAP.md` и `docs/roadmap/README.md` тем же пакетом.
- Соблюдать протокол прозрачности из `docs/roadmap/ENGINEERING_RULES.md` §4A: сообщать этап/work package, реальное состояние, субагентов, commit/CI и номер следующего шага; при команде «продолжай/работай по плану» самостоятельно переходить к следующему безопасному пакету.

Подробности: `docs/roadmap/ENGINEERING_RULES.md`.

## Git

- Не работать прямо в `main`.
- Не использовать force-push, reset hard или переписывание истории без прямого разрешения.
- Формат коммитов: `type(scope): result`, например `docs(roadmap): establish delivery phases`.
- Допустимые type: `docs`, `test`, `fix`, `refactor`, `feat`, `chore`, `build`, `ci`.
- Один коммит имеет одну проверяемую цель; не добавлять generated/cache/debug files.
- Перед коммитом просмотреть `git diff --check`, `git status --short` и staged diff.

## Проверка

Выбирать проверки пропорционально риску, но не заявлять завершение без свежего вывода. Полный gate:

```bash
composer validate --strict --no-check-publish
composer audit
composer migrate
composer test
composer analyse
composer lint
php bin/check-architecture.php
composer baseline:check
```

`composer migrate` обязателен перед `composer test`: интеграционный `MigratedSchemaTest`
проверяет фактически применённую схему, и без него локальный gate даёт ложнопадение на
дрейфе БД (CI всегда применяет миграции до PHPUnit).

Если часть gate пока сломана baseline-состоянием, зафиксировать это в `STATUS.md`; не выдавать старую поломку за результат текущего изменения.

`bin/check-module.php` пока не существует: его контракт и реализация относятся к этапу 03. Нельзя включать несуществующую команду в заявляемый пройденным gate.

UI-изменения дополнительно проверяются в реальном браузере на 390×844 и desktop. Платежи — только sandbox fixtures до отдельного production gate.

## Документация и память

- `ARCHITECTURE.md` описывает фактическое состояние, а не желаемое.
- Phase-файлы описывают план; не записывать будущую архитектуру как уже существующую.
- Существенные решения добавлять в `DECISIONS.md`.
- Важные решения и уроки сохранять в agentmemory, не включая персональные или секретные данные.
- `graphify-out/` остаётся локальным и не попадает в Git, но граф не считается актуальным автоматически: после work package с изменениями кода, шаблонов, CSS или документации выполнить `php bin/check-graphify-freshness.php` и обновить Graphify до `CURRENT` либо явно записать техническую причину, срок и безопасный fallback в `WORKLOG.md`.
- Если код расходится с документацией, исправить документацию в том же work package либо зарегистрировать отдельный долг в active phase.
- По команде владельца «сделай checkpoint» выполнить протокол из `docs/roadmap/CHECKPOINT.md`: обновить status/worklog/решения/уроки, записать проверки и точное dirty-state; не создавать незавершённый коммит автоматически.
- `CHANGELOG.md` описывает только проверенный эффект понятным владельцу языком; технические действия и незавершённая работа идут в `WORKLOG.md`.
- Не имитировать фоновую работу: после итогового ответа прямо указывать, что выполнение ожидает следующего сообщения, если текущая среда не поддерживает активный monitor.

## Когда нужен вопрос владельцу

Спросить до действия, если выбор меняет клинический смысл, scoring/norms, публичное обещание, объём передаваемых ИИ данных, фискальные настройки, production-инфраструктуру или утверждённый SMIL-график. Обычные обратимые инженерные решения выполнять самостоятельно в рамках phase-файла.
